# Как это работает
Специальность 09.02.07. Портал «Конференции.РФ».
Этот документ объясняет **почему** проект устроен именно так.
`INSTRUKCIYA.md` отвечает на вопрос «что напечатать».

Соберан скриптом `tools/docgen.py`.

## 1. Что происходит, когда открывается страница

Один запрос проходит шесть остановок. Порядок важен: сломается
любая — и страница не откроется.

```
браузер: GET /applications/
   │
   ▼
1. CommonMiddleware — добавляет слеш в конце, если его нет
   │
   ▼
2. SessionMiddleware — находит или создаёт cookie сессии
   │
   ▼
3. AuthenticationMiddleware — читает сессию и кладёт в request.user
   │                                  ← вот он, пользователь
   ▼
4. MessageMiddleware — достаёт сообщения прошлого запроса
   │
   ▼
5. portal/urls.py → main/urls.py → views.applications
   │
   ▼
6. представление спрашивает базу и передаёт шаблону
   │
   ▼
templates/applications.html собирает страницу
```

**Что из этого важно понимать.**

Пункт 3 объясняет, почему в шаблоне можно писать
`{{ user.username }}`: пользователя туда положил Django, а не ты.
И почему гостя видно без всяких проверок — у него
`user.is_authenticated` равно `False`.

Пункт 5 объясняет, почему представление не знает про HTML: его
дело — получить данные и выбрать шаблон.

**Что происходит при отправке формы.** Тот же путь, но в
представлении `request.method` равен `"POST"`, а
`request.POST` — словарь с тем, что ввёл человек. Форма
приходит в `request.POST` уже разобранной, собирать её вручную
не нужно.

## 2. Кто за что отвечает

| Файл | Отвечает за | Не отвечает за |
|---|---|---|
| `portal/settings.py` | что подключено, где база, где шаблоны | логику страниц |
| `portal/urls.py` | общий список адресов и раздача статики | что делает страница |
| `main/urls.py` | адреса приложения | логику |
| `main/models.py` | как выглядит таблица | что с ней происходит |
| `main/forms.py` | как выглядит форма и какие поля проверяются | что делать с результатом |
| `main/views.py` | логика: что показать, что сохранить | разметку страницы |
| `main/validators.py` | форматы полей из задания | всё остальное |
| `templates/*.html` | как это выглядит | логику и запросы к базе |
| `static/style.css` | вид сайта | содержимое страниц |
| `static/app.js` | подтверждение смены статуса | всё остальное |
| `api.py` | модуль 4 целиком | портал |

Правило простое: **в шаблоне не бывает запросов к базе, в
представлении не бывает разметки.** Если в шаблоне понадобился
запрос — это сигнал, что данные надо было передать из
представления.

## 3. Что Django создал сам, а что пишешь ты

Это главный вопрос, который экономит время на экзамене.

**Создаётся само — не пиши руками:**

| Что | Командой |
|---|---|
| `manage.py` | `startproject` |
| `portal/wsgi.py`, `asgi.py`, `__init__.py` | `startproject` |
| `main/apps.py`, `__init__.py` | `startapp` |
| `main/migrations/` | `makemigrations` |
| таблица `auth_user` | `migrate` |
| таблицы в PostgreSQL | `migrate` |
| файлы `.po` при `makemessages` | — |

**Пишется руками:**

| Файл | Что в нём |
|---|---|
|---|---|
| `main/models.py` | две таблицы |
| `main/views.py` | семь представлений |
| `main/urls.py` | семь адресов |
| `main/forms.py` | четыре формы |
| `main/validators.py` | форматы полей |
| `portal/settings.py` | правится созданный |
| `portal/urls.py` | правится созданный |
| `templates/*` | семь файлов |
| `static/style.css` | 223 строки |
| `mobile/*` | пять файлов |
| `api.py` | 151 строка |

**Создаётся само, но всё равно надо поменять:**
`INSTALLED_APPS` (дописать `main`), `DATABASES` (чтобы указывать
путь к файлу явно), `TEMPLATES` (`DIRS` с папкой `templates`),
`STATICFILES_DIRS`, `LOGIN_URL`.

**Всё остальное Django делает по умолчанию**, и это нормально:
`ALLOWED_HOSTS`, `SECRET_KEY` при `DEBUG = True`, `WSGI_APPLICATION`,
`USE_I18N`, `USE_TZ`. Дописывать их не нужно — только лишний код,
который придётся запоминать.

## 4. Как придумать таблицы из задания

Способ, который работает на любой похожей задаче: прочитать
текст и выписать каждое существительное, которое можно сохранить.

**Что говорит задание про пользователя:** «Логин указывается
пользователем. Имя — строка, содержащая символы кириллицы»,
«после успешной регистрации пользователь попадает в
авторизованную зону».

Вывод: нужна таблица пользователей. Но она уже есть —
`auth_user`. Свою создавать не надо.

**Что говорит задание про заявку:** «пользователь указывает нужное
помещение, введя его название в соответствующее поле», «указывает
желаемую дату начала конференции», «должен выбрать удобный способ
оплаты: при очном посещении или переводом по системе СБП».

Три поля. Плюс два, которые следуют из других фраз:

| Фраза в задании | Поле |
|---|---|
| «свои ранее оставленные заявки» | `user` |
| «Новая», «Мероприятие назначено», «Завершено» | `status` |

**Что говорит задание про отзыв:** «оставить отзыв о качестве
проведённого мероприятия».

Таблица отзывов нужна. «О качестве» — это оценка, плюс текст.
Связь с заявкой один-к-одному: отзыв оставляют один раз и только
после завершения.

**Итог: две таблицы плюс стандартная `auth_user`.**

Чего в задании нет, поэтому нет и в проекте: справочник
помещений (пользователь сам вводит название), тип помещения,
комментарий к заявке, дата создания. Проверяющая система по
ним не спрашивает, а держать в голове лишнее — это риск.

**Правило для проверки.** Задай себе вопрос: «показывает ли это
поле где-нибудь на экране?» Если нет — оно не нужно.

## 5. Как придумать страницы

Та же логика. В задании пять экранов:

| Экран | Адрес в проекте |
|---|---|
| Страница регистрации | `/register/` |
| Страница авторизации | `/login/` |
| Страница просмотра заявок | `/applications/` |
| Страница формирования заявки | `/application/new/` |
| Панель администратора | `/admin/` |

Плюс два технических: `/` перекидывает на нужную страницу и
`/logout/` завершает сеанс. Без выхода зайти повторно нельзя.

**Что делает каждая страница по заданию:**

Регистрация — форма из пяти полей, при правильном заполнении
создаёт пользователя и уводит на страницу входа.

Авторизация — логин и пароль, при успехе пускает в закрытую
зону.

Просмотр заявок — список своих заявок, изменение, удаление,
а после завершения — форма отзыва.

Формирование заявки — три поля, кнопка «Отправить».

Панель администратора — все заявки всех пользователей и смена
статуса.

## 6. Как придумать проверки

Автотест проверяет поведение, а не код. Поэтому проверять надо
то, что реально происходит: что поле нашлось, что данные
сохранились, что гостя не пустили.

| Задание | Что проверяется | Как это выглядит в тесте |
|---|---|---|
| регистрация | поля с `data-testid` есть | ищем их в HTML страницы |
| регистрация | ошибки показываются | отправляем заведомо кривые данные, ищем текст ошибки |
| вход | сессия работает | входим и открываем закрытую страницу — должна открыться, а не 404 |
| CRUD | строка появилась | считаем записи в таблице до и после |
| отзыв | только после завершения | пробуем оставить отзыв на новой заявке — должен не получиться |
| админ | обычному пользователю закрыто | входим пользователем, открываем `/admin/` — должен быть 403 |
| адаптив | нет горизонтальной прокрутки | сравниваем ширину страницы и окна |

**Две проверки, которые пишутся в первую очередь**, потому что
ломаются чаще всего: гость не должен видеть закрытую страницу,
и обычный пользователь не должен попасть в панель
администратора.

Готовая проверка — `tools/check_autotest.py`, 46 проверок.

## 7. Чек-лист для похожего проекта

Порядок действий, который работает на любой похожей задаче.

- [ ] Прочитать текст задания целиком, выписать все поля форм
- [ ] Составить таблицы: что сохраняем, что только показываем
- [ ] `startproject` и `startapp`
- [ ] Настроить `settings.py`: приложение, база, шаблоны, статика, `LOGIN_URL`
- [ ] Написать модели, `makemigrations`, `migrate`
- [ ] Проверить, что таблицы появились
- [ ] Написать формы с `data-testid` на каждое поле
- [ ] Написать проверки форматов по тексту задания
- [ ] Написать представления, по одному на экран
- [ ] Прописать адреса, все со слешем
- [ ] Сделать `base.html` и подключить его ко всем страницам
- [ ] Проверить, что страницы открываются по одному
- [ ] Наполнить базу демонстрационными данными
- [ ] Открыть каждую страницу в браузере и посмотреть глазами
- [ ] Проверить адаптивность на трёх ширинах
- [ ] Нарисовать ER-схему по фактическим таблицам
- [ ] Собрать архивы, проверить, что в `project_1.zip` есть `.git`

## 8. Проверка: что ты теперь умеешь

Семь вопросов. Если на любой из них ответ «не знаю» — вернись
к соответствующему разделу.

1. Куда Django отправляет гостя на закрытой странице и почему
   без `LOGIN_URL` получается 404?
2. Почему адрес должен оканчиваться слешем?
3. Чем `create_user` отличается от `create`?
4. Почему в `clean()` пишут `data.get()`, а не `data[...]`?
5. Куда девается ошибка «логин уже занят», если в шаблоне нет
   `form.non_field_errors`?
6. Какая строка в `applications` не даёт удалить чужую заявку?
7. Почему отзыв проверяется в представлении, а не только в
   шаблоне?

Если все семь ответов есть — пора собирать проект.
